1Organizar las carpetas

Las pruebas buscan la aplicación en ..\..\Hackaton respecto a la carpeta de pruebas. Lo más fácil es dejar esta estructura:

playwright\
├── Hackaton\              (la aplicación auditada)
└── auditoria\
    └── auditoria-qa\      (este proyecto)
mkdir playwright; cd playwright
git clone https://github.com/MrRoar154/Hackaton.git
mkdir auditoria; cd auditoria
git clone https://github.com/Fredpuff/auditoria-qa-campus.git auditoria-qa
cd ..

Si la aplicación queda en otro lugar, indícalo antes de correr las pruebas:

$env:APP_DIR = "C:\ruta\a\Hackaton"   # Linux/macOS: export APP_DIR=/ruta/a/Hackaton

2Encender la aplicación en el commit auditado

cd Hackaton
git checkout 16ebe4d
copy .env.example .env     # Linux/macOS: cp .env.example .env
npm install
npm run db:up              # PostgreSQL 16 + pgvector en Docker (puerto 5434)
npm run db:deploy          # crea las tablas
npm run db:seed            # 2 sedes, 38 espacios, 10 usuarios, 63 incidencias
npm run dev                # API http://localhost:4000 · web http://127.0.0.1:5173

Deja esta terminal abierta. En otra terminal comprueba que la API responde:

curl.exe http://localhost:4000/api/health   # {"status":"ok",...}

Abre http://127.0.0.1:5173. Todos los usuarios de prueba usan la contraseña campus123 (por ejemplo supervisor@campus.edu.co).

El .env se copia tal cual de .env.example, como dice el README de la aplicación. Esa configuración es la que deja ver BUG-04 (acceso rápido) y BUG-05 (secreto JWT de ejemplo).

4Correr la suite completa

npx playwright test

Qué hace, en orden:

  1. Recarga los datos de ejemplo (npm run db:seed en Hackaton), porque los SLA vencen con el reloj.
  2. Inicia sesión con 8 usuarios y espera 61 segundos (caché de espacios de la API y límite de 10 ingresos por minuto). Es normal que la consola se quede quieta.
  3. Corre los casos de API (tests/api) y de la web (tests/e2e), uno por uno.
  4. Al final espera otro minuto y corre los 2 casos del bloqueo de ingresos (tests/limite).

7Tres ejecuciones + cobertura de la API

La cobertura arranca la API con c8, así que la API no puede estar corriendo antes.

  1. En la terminal de la aplicación, detén npm run dev con Ctrl + C.
  2. Deja solo la web: 
    cd playwright\Hackaton
npm run dev -w @campus/web
  3. En la terminal de las pruebas: 
    npm run cobertura           # una ejecución con cobertura
npm run tres-ejecuciones    # tres seguidas con cobertura (~15 min)

El script arranca la API con c8 a través de cobertura\servidor-api.mjs, que solo importa apps/api/src/main.ts sin modificarlo; corre la suite y apaga la API limpiamente.

DóndeQué hay
cobertura\reporte-api\index.htmlReporte HTML de cobertura (doble clic)
cobertura\reporte-api\resumen-consola.txtTabla por archivo y totales
resultados\ejecuciones.jsonDuración y código de salida de cada ejecución

Referencia: líneas 85,82 %, ramas 82,3 %, funciones 91,66 %. Entre ejecuciones es normal ver Ingreso bloqueado por la ejecución anterior; esperando 53 s.

Al terminar, detén la web sola y vuelve a encender todo con npm run dev.

8GitHub Actions

El flujo .github\workflows\pruebas.yml hace todo en un servidor de GitHub: PostgreSQL con pgvector, la aplicación en el commit 16ebe4d, los datos, la API, la web y la suite.

  • Se ejecuta solo con cada git push a main.
  • A mano: pestaña Actions → Pruebas de la auditoría → Run workflow.
  • Termina en rojo porque fallan los 11 casos de los defectos; es lo esperado. Los reportes se descargan en Artifacts (reportes-auditoria).

10Apagar todo

# En la terminal de la aplicación: Ctrl + C para detener npm run dev
cd playwright\Hackaton
docker compose stop postgres   # apaga la base sin borrar datos

Para borrar también los datos: docker compose down -v (luego hay que repetir db:up, db:deploy y db:seed).
